**What you did:**

You refactored your app so it works identically across four environments (local dev, Docker, Minikube, EKS) without changing code per environment.

Specifically:
1. Changed `apiBaseUrl` from `http://localhost:5000/api` to `/api` (relative path)
2. Added `proxy: http://localhost:5000` to `package.json` for local dev
3. Created `nginx.conf` to handle routing in Docker/K8s (serve React + proxy `/api` to backend)
4. Switched frontend Dockerfile from `npm start` (dev server) to multi-stage build with nginx (production server)
5. Updated docker-compose port mapping from `3000:3000` to `3000:80` to match nginx
6. Made sure backend service is named `fcms-backend` consistently across Docker and K8s

---

**Why each change was needed:**

**1. Hardcoded `localhost:5000` was the root problem**

In Docker Compose, you and the user are the same person on the same machine, so `localhost:5000` accidentally worked. But code that runs in a user's browser can't assume the backend is on the user's own laptop — that's only true for you, the developer. In K8s/production, the user is somewhere else in the world. `localhost` becomes meaningless.

**2. Relative path `/api` solves the location problem**

`/api` says "call this on whatever domain I'm currently on." This makes the frontend portable — it doesn't need to know if it's running locally, in Docker, or in EKS. The infrastructure (Webpack proxy / nginx / Ingress) handles the actual routing.

**3. nginx with custom config replaces the dev server**

`npm start` is React's development server — slow, debug mode, includes hot-reload, ships with the entire Node runtime. Fine for local development, terrible for production. Real apps build static files and serve them with a proper web server (nginx). Your nginx config does two jobs: serve the React build, and reverse-proxy `/api` to the backend container.

**4. The hostname `fcms-backend` in nginx.conf is the glue**

When nginx says `proxy_pass http://fcms-backend:5000`, it relies on DNS to find what `fcms-backend` actually is. Docker Compose creates that DNS entry from the service name. K8s creates it from the Service object name. By using the **same name** in both places, the SAME nginx config works in both environments — no environment-specific builds.

**5. Multi-stage Dockerfile = smaller, safer images**

Stage 1 builds React (needs Node). Stage 2 serves it (only needs nginx). Final image has only what's needed for production — ~30MB instead of ~500MB. No Node runtime, no npm vulnerabilities, just nginx + your static files.

**6. The `proxy` in package.json keeps `npm start` working**

Without it, `npm start` would call `/api` and fail (Webpack dev server doesn't know what to do with it). The proxy line tells Webpack "any unknown path, forward to `localhost:5000`." So local dev still works, but with relative paths instead of hardcoded URLs.

---

**The bigger picture — why this matters for your career:**

The pattern you just implemented is **the standard production setup** for any React + API app. Every company doing serious deployments uses this:

- Frontend is built into static files
- nginx (or a CDN) serves those files
- nginx (or a load balancer) reverse-proxies `/api` to the backend
- Frontend code uses relative paths so it's environment-agnostic

You can now confidently say in interviews: "I refactored my React app to use relative API paths and nginx as a reverse proxy, making the same Docker image work seamlessly in local dev, Docker Compose, Minikube, and EKS without environment-specific code." That's a real production engineering decision, not just "I followed a tutorial."

- Future improvements (HTTPS, CDN, multi-region) plug in cleanly because the foundation is correct
